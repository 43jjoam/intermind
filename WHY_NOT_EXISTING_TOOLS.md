## Question

> What specific capability does Intermind require that these tools do not already provide adequately?

Compare this experiment with:

### Git commits

Already provide: snapshot history, diffs, blame, revert, and reconstructible CREATE/EDIT/MOVE if history is not force-rewritten.

Ask: what does a Challenge-to-span relationship need that a commit plus a quoted string does not already give?

### GitHub Issues

Already provide: threaded discussion, labels, open/closed state, assignment.

Ask: does Issue “closed” collapse address claims into a truth-like verdict? Can an Issue comment keep a frozen `quoted_target` and `target_version_id` across file revisions without retargeting?

### Pull Requests

Already provide: proposed revision, review, inline comments on a specific diff line, merge lineage.

Ask: do inline review comments survive later edits of the same conceptual claim once the line has moved, split, or been paraphrased? Is that the same problem as Stage-0 span persistence?

### Review comments

Already provide: line-anchored critique, sometimes outdated-comment markers.

Ask: is “outdated comment” enough for a later reader to know whether the Challenge still applies, or does it only say the line number changed?

### RFC processes

Already provide: versioned documents, explicit discussion, consensus or disagreement notes, supersession.

Ask: what does Intermind’s Challenge grammar add that an RFC plus last-call discussion does not, at this scale?

### Wiki / talk-page history

Already provide: current page versus history, talk-page objection, often silent overwrite of the “current” article.

Ask: does a separate talk page preserve the objection next to the claim a late reader actually sees, or does it hide unresolved state?
